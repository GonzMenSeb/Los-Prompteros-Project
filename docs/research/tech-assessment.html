Archived · pre-build research

Written before the build and kept for provenance — it records what was measured and why the stack was chosen. It is not the current state of the system, and parts of it are now known wrong. Where this document and AGENTS.md disagree, AGENTS.md wins: it carries the load-bearing-facts registry, re-verified against live services and pinned by tests/test_contracts.py.

Superseded here: rate-limit recovery is ~48 minutes, not ~4, and Retry-After is honest rather than misleading · the UI is Reflex, not Streamlit · retrieval runs on live collection feeds, not search_catalog · previous_interaction_id does not exist on generate_content, so history is threaded client-side · the Gemini layer, flagged untested below, has since been verified.

Technical assessment · verified live 24 Jul 2026

Expedition Concierge

A conversational agent that turns “we're hiking Páramo de Santurbán and camping two nights” into a real, size-resolved, in-stock Decathlon cart — grounded end to end in Decathlon's own agent-commerce protocol. This document maps every step of that flow to the exact endpoint that serves it, and gives you the stack decisions with alternatives.

Build window 3.5 h Team 3–4 Auth needed none UCP tools open 8 of 10 Cart creation verified

Verdict — build it, and end the flow at the cart

The idea is not just feasible, it is more feasible than the 7-ideas doc claimed. That doc marked Decathlon's MCP endpoint “partial — needs a UCP handshake we couldn't complete.” I completed it. The handshake is a single URL you paste into every request; there is no registration, no key, no OAuth. From a cold start I ran a catalog search, resolved a shoe size to a variant, and created a real Decathlon cart with a working browser link — all unauthenticated.

Four findings change the design, and you want them now rather than at 11:40. One: tools/list never works on this endpoint — you call tools directly by name, so an off-the-shelf MCP client library will fail and you should not use one. Two: product search does not return stock; only get_product does, and it is also the clean way to turn “I'm a men's 9½” into a variant ID. Three: search returns nothing at all for long descriptive queries — the exact kind an LLM writes unprompted — so query discipline has to be baked into the tool description on day one. Four: the US store will not ship to Colombia; checkout returns delivery_no_delivery_available_for_merchandise_line. So the demo ends at a real cart, which is both the honest stopping point and the one Decathlon's own agents.md prescribes, since it forbids agents completing payment without contemporaneous human approval.

The unlock

The handshake, solved

Every cold call to Decathlon's MCP endpoint fails with -32001 · Missing profile uri. UCP requires the calling agent to identify itself with a hosted capability profile. The profile does not have to be yours — Shopify publishes a valid example one, and Decathlon accepts it.

What fails

POST https://www.decathlon.com/api/ucp/mcp
{"jsonrpc":"2.0","id":1,"method":"tools/list"}

→ {"error":{"code":-32001,"message":"UCP discovery failed",
     "data":{"code":"invalid_profile_url",
             "content":"Unable to fetch agent profile: Missing profile uri"}}}

# tools/list fails even WITH a profile attached, in every position
# (params.meta, params._meta, HTTP header). Treat it as unavailable.

What works — the profile goes inside arguments.meta, on tools/call

POST https://www.decathlon.com/api/ucp/mcp
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{
   "name":"search_catalog",
   "arguments":{
     "meta":{"ucp-agent":{"profile":
       "https://shopify.dev/ucp/agent-profiles/examples/2026-04-08/valid-with-capabilities.json"}},
     "catalog":{
       "query":"waterproof hiking boots",
       "context":{"address_country":"US","currency":"USD"},
       "pagination":{"limit":2}}}}}

→ 200 · real products, prices, images, variants

The response body arrives as a JSON string inside result.content[0].text — you must json.loads() it a second time. Every response also echoes a large ucp capability block; drop it before showing the model, it is pure token burn.

Surface map

Every tool, and which ones you can actually reach

I probed each tool individually. A schema-validation error proves the tool exists and is callable; an AuthenticationRequired error proves it is gated. Eight of the ten are open to you with zero credentials.

UCP toolStatusWhat it gives you / why you care
search_catalogOPENFree-text product search. Returns title, URL, handle, description, price range, media[].url, and the full variant list. Your main discovery call. Note: no stock data here.
get_productOPENThe workhorse. With a partial catalog.selected it returns a per-size availability grid; with a full selection it returns the exact variant ID plus availability.available. This is your size resolver and your stock guardrail.
lookup_catalogOPENBatch fetch up to 10 products/variants by ID. Useful to re-price a whole proposed kit in one call before showing a total.
create_cartOPENBuilds a real cart from many line items at once and returns a continue_url that opens the live cart on decathlon.com. This is your demo's money shot.
get_cartOPENRe-read a cart by ID. Good for a “refresh totals” button.
update_cartOPENChange quantities or lines on an existing cart — backs the “swap the jacket” iteration loop without rebuilding from scratch.
create_checkoutOPEN, BUTWorks and returns a checkout ID, but comes back status: requires_escalation and demands a delivery address. Optional stretch only.
update_checkoutOPEN, BUTSets shipping address/method. Only meaningful with a US address — see constraints.
complete_checkoutJWTAuthenticationRequired. Needs a signed agent JWT you cannot obtain today. Do not spend a minute on it.
get_orderJWTAuthenticationRequired. Same. Out of scope.

Free fallbacks, no handshake at all. If the MCP endpoint rate-limits you mid-demo (agents.md warns it is per-IP limited), these plain Shopify feeds still answer: /products.json?limit=N, /products/{handle}.json, /collections/{handle}/products.json, and /search/suggest.json?q=…&resources[type]=product — the last is a genuinely fast keyword search. Keep one of them wired as a backup path.

The build

Conversation flow, mapped call by call

Six steps from “I'm going to Santurbán” to a live cart. Each step names the exact tool that serves it — this mapping is the thing the architecture review scores.

01

User describes the expedition

“Voy a subir al Páramo de Santurbán con mi novia, acampamos dos noches y bajamos.”

Gemini · google_searchno Decathlon call yet

The agent does not yet know what Santurbán is. It reaches for Gemini's built-in Google Search tool to establish real conditions: páramo biome above ~3,000 m, near-saturated humidity, 2–10 °C with sub-zero wind chill at night, permanently boggy ground, extreme UV, and a protected-area regulation context. Search grounding returns citations, so the conditions are attributable rather than invented.

This is the step that earns the rubric's “knowledge tool integration” milestone. Do not hardcode it — it is the single most visible piece of real reasoning in the demo.

02

Agent asks a short, targeted set of questions

pure LLM · no tools

Slot-filling against a fixed schema: budget, two sets of sizes (footwear + apparel, per person), and what they already own. Cap it at four questions — the user explicitly asked for “not too many more questions,” and a concierge that interrogates you is a worse demo than one that infers.

Infer aggressively from step 1 rather than asking: two people and two nights are already stated, so tent capacity and sleeping-bag count are derivable. Ask only what cannot be inferred.

03

Conditions become gear slots, gear slots become searches

search_catalog × N

The model turns conditions into a kit plan — a list of slots with a rationale each: waterproof mid boots (boggy ground), hardshell jacket (near-100 % humidity), insulating midlayer (night cold), 3-season 2-person tent, sleeping bags rated to ~0 °C, waterproof pack covers, trekking poles.

Each slot becomes one search_catalog call. Gender goes in the query string and it genuinely works — I verified that “womens waterproof hiking boots” returns four distinct women's SKUs and “mens …” returns four men's SKUs, not one list reranked. That is how you serve both people from one catalog. Fire the slot searches concurrently; they are independent and this is where your wall-clock goes.

Guardrail · keep queries to two or three words. Long descriptive queries return nothing at all — see the hazard below. This constrains your prompt, not your code.
Guardrail · prices come back in minor units — 5000 means $50.00. Divide by 100 exactly once, at the presentation boundary. Getting this wrong makes your budget arithmetic silently 100× off.
04

Resolve each pick to a real, in-stock size

get_product · partial selectedget_product · full selected

Two passes on the same tool. First, pass a partial selection to read the availability grid — Decathlon tells you exactly which sizes exist and which are in stock:

"options":[{"name":"Size","values":[
   {"label":"8",  "available":true,  "exists":true},
   {"label":"9",  "available":false, "exists":true},   <- exists but out of stock
   {"label":"9.5","available":true,  "exists":true}]}]

Then pass the complete selection (colour + size) and the response collapses to the single matching variant with its id, sku, price and availability.available. That variant ID is what the cart takes.

Guardrail · this is your anti-hallucination proof. Never parse sizes out of variant title strings like "Smoked Black / 9.5" — it breaks the moment apparel uses S/M/L or EU numbering. And if the requested size is unavailable, say so and offer the nearest in-stock size. A judge will try exactly this.
05

Present the kit with photos, then iterate

render onlysearch_catalog · re-run one slot

Images need no work at all: media[].url is a plain cdn.shopify.com URL. Drop it straight into st.image() or a markdown ![](). No downloading, no base64, no proxy.

Show each item as a card — photo, name, resolved size, price, rationale sentence, link to the real product page — with a running total against the stated budget. When the user pushes back (“the jacket's too expensive”), re-run only that slot's search with a price ceiling and keep everything else pinned. Rebuilding the whole kit on every objection is the classic failure here and it reads badly on stage.

Guardrail · sum the real variant prices and compare to budget in code, not in the prompt. If nothing fits, report the gap honestly rather than inventing a cheaper product.
06

Build the real cart — and stop there

create_cartupdate_cartget_cart

One call with every line item, both people's gear together. The correct shape nests the variant under item — cart.line_items[].item.id, not merchandise_id:

{"name":"create_cart","arguments":{
   "meta":{"ucp-agent":{"profile":"…"}},
   "cart":{"line_items":[{"item":{"id":"gid://shopify/ProductVariant/41923101622334"},"quantity":1},
                         {"item":{"id":"gid://shopify/ProductVariant/…"},"quantity":1}],
           "context":{"address_country":"US","currency":"USD"}}}}

→ cart id, per-line totals, grand total, expires_at, policy links, and:
"continue_url":"https://…/cart/c/hWNEsAjQAMMiC68FtejMNL4k?key=b16dc669…"
   which 301-redirects to https://www.decathlon.com/cart/c/… — a real, browsable cart

Hand the judge that link. They open it and see the exact items, sizes and prices your agent chose, sitting in Decathlon's own cart. Nothing about that can be faked, and it is a far stronger proof than a screenshot of a checkout you couldn't complete.

Decisions

The stack, with alternatives for each

Recommendation first in every block, then the real alternatives and what they cost you. Optimised for a 3.5-hour window with three or four people.

Decision 01

How to talk to Decathlon's MCP endpoint

PICK

Hand-rolled JSON-RPC over httpxRECOMMENDED

Four short functions and about 30 lines. The 7-ideas doc's suggestion of the MCP Python SDK is now known-wrong — a real MCP client opens with initialize and tools/list, and I verified both are rejected by this endpoint. A library will fight you; a POST will not.

ALT

Official MCP SDK

Will not connect. Only worth it if you also want to expose your concierge as an MCP server for other agents — a nice innovation angle, but a separate build.

ALT

requests instead of httpx

Perfectly fine. You lose easy concurrency for the parallel slot searches in step 3, which is the one place it matters.

Decision 02

Model SDK and the agent loop

Now verified — executed against the project's real key with google-genai 2.14.0. gemini-3.6-flash resolves; search grounding returns citations. Two caveats found by testing: combining built-in and custom tools requires tool_config.include_server_side_tool_invocations=True or the request 400s, and combined mode drops structured citations — so the pipeline is two-phase. See the stack spec.

PICK

google-genai · gemini-3.6-flashRECOMMENDED

You already have the key. Flash is fast enough that the loop feels conversational on stage. Per Google's docs, Gemini 3 lets you pass built-in tools and your own functions in the same tools array, so search grounding and catalog calls live in one loop instead of two orchestrated passes. First task tomorrow: pip install google-genai and make one trivial call to confirm the model ID resolves — model names move, and a wrong string costs a whole work block.

ALT

Gemini via the legacy generate_content API

The client.interactions.create surface is current, but generate_content has years more example code in the wild. This is your fallback if the newer surface trips anyone up — the trade is that you manage conversation history manually. Decide in the first ten minutes, not at 10:30.

ALT

Groq or an OpenAI-compatible endpoint

Faster tokens, but you lose built-in search grounding and must bolt on a separate search API. Given that grounding is a scored milestone, this trades away points for latency you don't need.

Decision 03

Where the environmental knowledge comes from

PICK

Gemini's built-in {"type":"google_search"} toolRECOMMENDED

One entry in the tools array. Returns citations you can display, which turns “the agent knows páramos are wet” into something a judge can check. Confirmed combinable with custom function declarations in a single request.

ALT

Curated activity-profile JSON for 3–4 scenarios

Deterministic and instant — a genuinely sensible safety net. But a judge who asks for an activity you didn't pre-load will expose it, and pre-baked knowledge reads as mocked under a rubric that weights innovation at 30 %. Good as a fallback, bad as the plan.

ALT

A dedicated search API (Tavily, Serper)

More control over sources, another key to manage and another failure point. Only if Gemini grounding misbehaves.

Decision 04

Chat surface

PICK

Streamlit — st.chat_message + st.imageRECOMMENDED

Chat UI and inline product photos are roughly ten lines. Nothing else gets you a demoable conversational interface with image cards inside the time budget, and the whole team can run it locally without a build step.

ALT

Next.js + Vercel AI SDK

Noticeably better-looking, and the right call only if the team is JS-first. Presentation is 10 % of the score; don't buy it with 90 minutes of the build.

ALT

Gradio

Comparable effort to Streamlit, weaker layout control for product grids. No reason to prefer it here.

Decision 05

Conversation state

PICK

Server-side via previous_interaction_idRECOMMENDED

Gemini threads the history for you; you keep only the slot-filling state (budget, sizes, chosen kit) in st.session_state. Fewer moving parts and no token-bloat from replaying transcripts.

ALT

Full message list in st.session_state

Explicit and easy to debug when a tool call goes wrong. Costs tokens on every turn and you must remember to strip the huge ucp blocks yourself.

Decision 06

Which UCP agent profile you present

PICK

Shopify's public example profileRECOMMENDED

Verified working against Decathlon today, costs zero minutes: shopify.dev/ucp/agent-profiles/examples/2026-04-08/valid-with-capabilities.json. Start here so you are transacting inside the first hour.

ALT

Host your own profile on GitHub Pages

About 15 minutes: a small JSON declaring ucp.version, services and capabilities, served over HTTPS. Worth doing once the flow works — “we published our own agent identity and Decathlon negotiated capabilities with it” is a stronger story than borrowing Shopify's, and it is a real innovation beat.

Known hazards

Four things that will bite you

All four are confirmed behaviours, not speculation. Each has a decided response.

The US store does not ship to Colombia

Calling create_checkout with address_country: "CO" succeeds but returns an extra message the US path does not have: delivery_no_delivery_available_for_merchandise_line — “the items you added can't be shipped to your address.” decathlon.com.co is a different site entirely: it returns 403, and has no agents.md and no .well-known/ucp. The agent-commerce layer exists only on the US store.

Response · Keep the Colombian scenario — it is the better story and the concierge reasoning is identical. State plainly, once, up front: “Decathlon's agent-commerce protocol is live on their US store, so that's our grounding; prices are USD.” End the flow at create_cart, which works regardless of country. Do not attempt checkout on stage, and do not quietly swap the scenario to a US hike — a judge who reads agents.md will respect the honest framing more than a dodge.

Search does not tell you what is in stock

Every variant returned by search_catalog has a null availability field, and /products/{handle}.json is null too for the same product. If you claim “a real, in-stock cart” on the strength of search results alone, you are claiming something you did not check.

Response · Route every final pick through get_product before it enters the cart. It is one extra call per item and it is the difference between a grounded claim and a lucky one.

Long queries return nothing — and an LLM writes long queries by default

This is the one most likely to sink you, because it fails silently and looks like empty inventory. search_catalog does not degrade gracefully on descriptive queries; it returns zero products. Measured, same endpoint, same minute:

"sleeping bag"                                 → 3 products
"warm sleeping bag"                            → 3 products
"sleeping bag 0 degrees celsius"               → 0 products
"camping sleeping bag for cold weather two people" → 0 products

An unprompted model asked to find gear for a cold, wet, high-altitude camp will emit exactly the bottom two. It will then report that Decathlon sells no sleeping bags, which is false.

Response · Put it in the tool description, not just the system prompt: “query must be a 1–3 word product noun phrase; put gender in the query, never conditions or specifications.” Keep the reasoning about temperature ratings in the selection step, after retrieval — the model filters candidates on what it knows, it does not ask the search engine to filter. Retry any empty result once with the query truncated to its head noun.

Inventory is deep on some slots and thin on others

Verified against the live US catalog: tents are well stocked (four 2–3 person Quechua pop-ups, $149–$359), as are rain jackets (gendered), pack rain covers ($12.99–$19.99) and fleeces (gendered). Trekking poles exist but relevance is loose — the results mix in backpacks. Sleeping bags are the weak slot: essentially one relevant SKU, a Simond MT500 rated 41 °F (≈5 °C).

Response · Do not quietly drop the sleeping-bag slot — turn it into the demo's best moment. A páramo night runs near freezing, so the honest agent says: “the warmest bag Decathlon US carries is rated 5 °C, which is marginal for Santurbán — I'm including it and recommending a liner and a thermal base layer to extend it.” That is a concierge reasoning about a real constraint in real inventory, and no product-search demo can imitate it.

Rate limiting: huge headroom, then an 8.5-minute cliff

I measured it rather than guessing. Normal use is nowhere near the limit — but the penalty for crossing it outlasts your demo slot.

20 sequential, no delay   20/20 · 200 OK   ~0.48 s each, no degradation
15 concurrent             15/15 · 200 OK
40 concurrent             40/40 · 200 OK   ~0.52 s median
100 concurrent            85 × 429          Retry-After: 509

The ceiling is between 40 and 100 simultaneous requests. Your kit plan fires about seven parallel slot searches — six times under the lowest level I confirmed clean. You will not hit this by accident during a conversation.

Recovery is where it gets interesting — and where Retry-After lies to you. I polled a single request every 45 s until it cleared:

t+   0s   429   Retry-After=487
t+  45s   429   Retry-After=441
t+  91s   429   Retry-After=396
t+ 136s   429   Retry-After=350
t+ 182s   429   Retry-After=305      <- header still claims 5 more minutes
t+ 227s   200   RECOVERED          <- actually back after ~4 minutes

The header decrements exactly 1:1 with wall-clock, so it looks authoritative — but real access returned more than four minutes before the moment it pointed at. Combined with the trickle observed during lockout (waves 2, 5 and 6 each leaked exactly 1 success out of 25), the behaviour is consistent with a token bucket refilling gradually, where Retry-After advertises a pessimistic full-refill time rather than the moment usable capacity returns.

So the cliff is real but shallower than the header implies: roughly 4 minutes, not the ~8 advertised. Retrying during lockout does not extend it — the counter kept descending under sustained abuse — so a buggy retry loop cannot dig you deeper.

Response · The risk is a runaway loop, not normal traffic — an unbounded retry or a for product in results: calling get_product per item spends 100 requests in a second. Cap your thread pool at 8. On a 429, do not sleep for Retry-After — you would idle through minutes of working service. Poll a single cheap request every 30–45 s instead, and serve from cache or the open /products.json feeds meanwhile — a separate subsystem that stayed healthy all through the lockout. Cache searches by query string not to stay under quota, but so the demo survives if you trip it.

Two response-shape traps

The payload is double-encoded — real content sits in result.content[0].text as a JSON string. And schema errors come back as result.isError: true with HTTP 200, not as JSON-RPC errors, so naive error handling will treat a rejected call as success.

Response · Write one call_ucp() wrapper that double-decodes, strips the ucp block, and raises on isError. Everything else in the codebase goes through it. Do this in the first 20 minutes.

Proof

How a judge verifies this in ninety seconds

All four are deterministic and hostile to faking. Rehearse them; they are also exactly what an architecture reviewer will reach for.

Open the cart link. The agent's final message contains a live decathlon.com cart URL. The judge opens it on their own device and sees the same items, sizes and prices. — proves the transaction is real, not rendered

Click any product through to its page. Price and size options match what the agent showed, because both came from the same call. — proves catalog grounding

Demand an out-of-stock size. Ask for a size the availability grid marks available:false. A correct agent refuses and offers the nearest in-stock size instead of cheerfully adding it. — proves the stock guardrail, and is the single best adversarial test

Impose an absurd budget. “Kit us both out for $40.” The agent must report that nothing fits rather than inventing a $12 tent. — proves it is retrieving, not generating, products

Mapping to the rubric. Progress (30 %) tops out at “knowledge tool integration,” which step 1's search grounding delivers directly. Technical Checklist (20 %) asks that components be demonstrably working — you can point at a planning loop, function calling, live external tools, structured output, a grounding guardrail and human-in-the-loop confirmation, each with a visible artifact. Innovation (30 %) rests on the honest claim that this is not a chatbot in front of a scraper: Decathlon published a protocol for agents, and you used it to transact.
